# Proposal：规则分层、目标一致性与 Fake-IP 稳定归属

日期：2026-11-07。状态：**待评审，供后续开发；未实施。** 基线：[master 8d018cd](https://github.com/xjdrew/kone/tree/8d018cd729f7417b7202a652c65a486ae0e2f33f)。问题编号沿用[研究报告第 3 节](../research/product-direction-2026-11-07.md#3-本次实验确认的四个边界)，用户已确认四个问题属实。

**建议采用固定四池：系统保护 → 域名 → IP → FINAL。** 同时必须补齐“需要解析时不能提前兜底”和“决定绑定具体地址”两个约束；只对规则重新排序不能完整修复 3.1、3.3。Fake-IP 建议采用稳定候选算法加持久地址归属，不能只换哈希函数。3.2 按用户决定保留为产品限制，后续写入用户手册。

## 1 四个问题与处置

| 编号 | 已确认的问题 | 原因判断 | 本 proposal 的处置 |
| --- | --- | --- | --- |
| 3.1 | 冷域名在 `IP-CIDR → direct`、`FINAL → proxy` 下，没有取得真实 IP 就选择 FINAL | 规则优先级与证据取得耦合，FINAL 被当作提前完成判断的依据 | 固定四池；域名池未命中且 IP 判断需要地址时先解析，只有确认不匹配后才进入 FINAL |
| 3.2 | 应用缓存真实 IP 后，新增域名规则不一定影响后续连接 | IP 报文没有原始域名；业务可能旁路或复用旧连接 | 明确产品限制、观察状态和重试说明；不通过猜测 IP 所属域名来绕过限制 |
| 3.3 | 根据 DNS 答案里的地址 B 命中 IP 规则，却拨号地址 A | 决定与地址选择分离；即使没有任何域名规则，问题仍可发生 | 决策输出必须携带获准的地址候选；拨号、重试和解释共用同一计划 |
| 3.4 | 重建映射后，旧 Fake-IP 可能归属于另一个域名 | 哈希碰撞、分配历史丢失及地址再分配；哈希本身不是随机的 | 持久化双向归属，在回复 DNS 前提交；缓存过期不等于可将地址交给其他域名 |

原始四个探针见[复现附件](../research/policy-boundaries-2026-11-07.md)。本次另外验证了“交换分配顺序会改变同一域名的地址”和“不重启也可能在过期回收后改变地址归属”，见[稳定性补充实验](../research/fake-ip-allocation-stability-2026-11-07.md)。

## 2 固定四池的规则语义

### 2.1 优先级与池内顺序

| 池 | 内容 | 顺序与权限 |
| --- | --- | --- |
| 系统保护 | 防环必需的出口/控制目标、本机及经网络上下文确认的保护范围 | 始终优先；由系统维护，不能被业务规则覆盖 |
| 域名 | DOMAIN、DOMAIN-SUFFIX、DOMAIN-KEYWORD | 保留池内用户顺序；命中后 IP 业务规则不再覆盖 |
| IP | IP-CIDR、IP-CIDR6、GEOIP | 保留池内用户顺序；不因文件中排在域名规则之前而取得跨池优先权 |
| FINAL | 显式兜底及原有范围外的默认行为 | 只在前面各池已完成判定后使用；不是“当前信息不足时先使用”的规则 |

同一池内继续首条匹配生效，不额外引入“精确域名自动高于后缀”“最长 CIDR 自动优先”等另一套排序。规则身份、到期状态、协议和端口条件保留。原有条件 FINAL 的范围外直连语义需要显式保留或在迁移时展开，不能静默扩大其范围。

只有真实 IP、没有可靠域名身份的输入，在系统保护后直接进入 IP 池；“域名优先”不要求先猜一个域名，也不要求做 PTR 查询。Fake-IP 则先恢复已知域名再按四池处理。这一区分保留问题 3.2 的产品限制。

例如，域名规则明确将 `service.example` 交给代理，即使其真实地址属于某条直连 IP 规则，也由域名规则决定。需要 `GEOIP CN → direct`、其余代理时，应使用 IP 池加 FINAL，而不是先放一个覆盖所有域名的代理规则。此优先级是可理解的产品选择，同时会改变部分旧配置的行为。

### 2.2 系统保护与 Fake-IP 的处理

先识别 Fake-IP 并恢复域名身份，再判断真实目标的保护规则；不能因 Fake-IP 位于私网/ULA 就将它当成普通局域网目标直连。

保护检查允许在取到新地址证据后再次执行。初始阶段检查已知目标；解析后及每次实际拨号前检查对应候选。固定四池规定的是优先级，不代表保护逻辑只能在不知道目标地址时执行一次。

如果某项保护依赖真实 IP，就必须取得相应证据，或者明确报告无法验证。域名规则可以跳过后面的 IP **业务规则**，不能跳过系统保护；也不能同时承诺“完全依赖代理远端解析、看不到真实 IP”和“已核实所有真实 IP 的本地/LAN 保护”。需要真实 IP 的场景必须使用符合私有解析范围和出口约束的解析路径。

保护集合沿用本机网络上下文及已有防环约束，本提案不把任意业务 IP 例外都升级成不可覆盖的系统规则。混合公网/私网答案逐候选处理，不能将一个地址的判定直接套到另一个地址。

### 2.3 CNAME 与缺少条件的处理建议

为避免冷热缓存导致同一显式域名规则改变结果，建议定义：**先以原始查询域名匹配域名池；有完整匹配即确定该域名动作。** 原始域名未命中时，才从合规解析取得的 CNAME 链补充别名匹配，再进入 IP 池。别名之间仍按域名池规则顺序匹配，只接受与本次查询关联的、有限长的链，不将无关 Answer/Additional 地址加入候选。

这是对现有“在所有域名/CNAME/IP 证据中比较全局序号”的行为调整，须在迁移预览与回归中说明。若希望原始域名与别名完全平级，则必须在可能存在更高优先级别名规则时先完成解析；不能一面保留这种语义，一面让冷域名提前走代理。本文推荐前一种、更确定的语义，作为评审点。

DNS 查询时不知道业务协议、端口或应用身份。一个可能命中但缺少条件的域名规则应返回“需要后续流信息”，必要时保留 Fake-IP；不能把 DNS 使用 UDP/53 当作业务连接的协议/端口，也不能将未知条件当成不匹配而提前进入 FINAL。现有 `@capture` 可作为延迟决定的实现参照。

应用仍是规则条件。本次不增加应用实现；带域名/IP 目标的应用条件可随目标进入相应池。**纯应用规则未来放在哪一层，需与 Smart/Custom 的规则规格一起确定**，不能在本次修复中暗设第五池或悄悄归入 FINAL。

## 3 3.1：显式表示“需要证据”

规则求值至少区分以下状态，具体类型名由实现确定：

| 状态 | 含义 | 后续动作 |
| --- | --- | --- |
| 已决定 | 条件完整且命中；仍遵守执行前保护检查 | 构造执行计划 |
| 未匹配 | 该池所需条件已经核对，确实未命中 | 进入下一个池 |
| 需要 DNS / 流信息 | 缺少判断该池的必要证据 | 解析或延迟到流阶段，不提前兜底 |
| 证据失败 | 必要解析超时、失败或无法安全表达私有解析范围 | 明确失败/不可判定，不伪装成未匹配 |

流程建议：

1. 固定配置版本，恢复 Fake-IP 身份并检查已知系统保护。
2. 检查原始域名规则；缺少业务条件时延迟决定。
3. 没有域名命中、但需要检查 CNAME/IP 时，按当前 DNS 上下文取得有效证据；没有可用缓存时才请求上游。
4. 检查新地址的保护条件，按已定义的域名/CNAME 语义决定是否进入 IP 池。
5. 对有效地址候选匹配 IP 池；确认未命中后使用 FINAL。

最小验收：`IP-CIDR 203.0.113.0/24 → direct`、`FINAL → office`，冷查询返回该网段地址时，必须先取得地址证据并选择直连。增加一个明确命中的代理域名规则后，域名池应优先于该 IP 业务规则。代理远端解析可以继续用于不需要本地地址证据的域名决定，但不能代替尚未完成的 IP 判断。

DNS 超时不等于 IP 不匹配；NXDOMAIN 不等于“外国目标”；GeoIP 返回未知国家才是一个可以继续后续 IP 规则/FINAL 的正常未匹配情形。首版不引入隐式 `no-resolve` 或“解析失败就忽略 IP 规则”的捷径，避免重新引入 3.1。

DNS、路由模拟、诊断和实际流处理应共享求值语义。模拟没有证据时显示“待解析/待业务条件”，不能输出一个看似确定的 FINAL 结果。

## 4 3.3：把规则决定与拨号地址绑定

建议决策输出一个不可变的执行计划，至少保留配置版本、规则池、规则 ID/池内顺序、原始域名、证据来源/有效期、选定动作和获准地址候选。`DomainRecord.RealIP` 的“第一个地址”不再独立决定实际拨号对象。

**推荐保留当前按规则优先级选择的方向，并补齐地址绑定：** 在 IP 池内按规则顺序寻找可匹配的有效地址，首条命中的规则胜出；候选集合只包含命中这条规则且通过保护检查、符合地址族的地址。同一规则允许多个地址时可逐个尝试；不能在这组地址失败后擅自拨号受不同规则约束的地址或换成直连。

这也意味着一条优先的 IP 拒绝规则若匹配答案中的候选，会拒绝本次按该规则决定的域名连接，而不是自动挑另一个地址规避。若未来想采用“先选地址、再独立路由”的策略，应另行明确其语义；本次不同时混用两种选择方式。

对于 3.3 的例子，`198.51.100.0/24 → direct` 命中 `198.51.100.9` 时，直连候选只能包含获准地址；不得直连答案里的 `203.0.113.9`。将 DNS 答案交换顺序不能改变这个约束。

还有一项必须覆盖：**若依据 IP 规则选择代理，也应把选定 IP 交给代理。** 只根据本地地址 A 判断，再把域名交给代理另行解析成 B，仍然可能重现同类问题。原始域名保留为身份和协议所需信息；TCP 字节转发不改写应用自己的 TLS SNI。只依据域名规则、且不需要真实 IP 保护证据的路径，才可明确采用代理远端解析，并将目标 IP 标为未知。

候选到期、网络/解析上下文变化时重新取证；已建立流继续使用旧快照。业务数据一旦转发，不自动重放到另一个地址。返回真实 DNS 答案时，也不能把“某个地址获准直连”的结果外推到整个答案集合；混合决定或需要保留域名身份的情况应使用 Fake-IP 将最终选择保留到流阶段。

## 5 3.4：稳定哈希只是候选 稳定归属才是目标

### 5.1 当前哈希已经稳定

`DnsIPPool.Alloc` 使用 `adler32(domain) % poolSize`；同一域名、相同字节和池大小会得到同一候选槽。槽被占用时再找空位，因此**最终地址取决于此前分配了哪些域名**。换成 SHA-256 可以改善候选分布，但截断到有限地址池仍会碰撞，而且哈希不能还原任意原始域名。[地址池](../../pkg/kone/dns_ip_pool.go)

本次在默认 `/16` 表和引擎保留地址条件下复现：`site-120.example` 先分配时取得 `10.192.97.89`；重建后先分配碰撞的 `site-201.example`，前者只能取得 `10.192.0.3`，旧地址已指向后者。相同顺序下地址不变。另一个实验在不重启的情况下，先过期回收前者，再将旧地址分给后者。[补充实验](../research/fake-ip-allocation-stability-2026-11-07.md)

因此需要同时处理重启和运行期回收；仅在退出时保存缓存，或每次启动使用相同哈希，都不足以满足目标。

### 5.2 推荐方案：持久化地址归属

| 方案 | 结果 | 取舍 |
| --- | --- | --- |
| 只换稳定哈希/扩大地址池 | 降低部分碰撞机会，不能保存碰撞分配结果或恢复反向域名 | 不作为 3.4 的完整修复 |
| 持久映射、到 TTL 后把地址给其他域名 | 通常重启稳定，但旧应用缓存仍可能错关联 | 只能承诺有限保留期，不能宣称消除 3.4 |
| 持久归属、同一池代次不将已发布地址改属其他域名 | 正常重启稳定；旧地址保持原身份或明确失败 | 推荐；需容量、损坏恢复与池迁移设计 |

建议实现一个与真实 DNS 缓存分离的地址归属账本：

- 以稳定池身份、地址族及规范化域名记录 `domain ↔ Fake-IP`；固定大小写/末尾点/IDNA 输入规则及算法版本，不随重启随机换种子。
- 首先复用已持久的地址。新域名可用标准库 SHA-256 选择候选，再按明确的冲突规则分配，并记录最终地址；正确性不依赖哈希永不碰撞。
- 只持久化域名与地址归属、池/格式版本及必要完整性信息；不把旧代理动作、真实 DNS 答案、GeoIP 结果或网络上下文当成重启后仍有效的决策。
- 内存解析缓存可以淘汰，地址归属仍保留；重新访问原域名可以恢复同一地址。清除 DNS 缓存和规则热更新不清除归属账本。
- 不同 profile/管理进程/CLI 若使用同一主机网络命名空间的同一地址池，必须共享归属或使用不重叠的池。只把状态文件放进各自 profile 目录，会把切 profile 变成另一种错关联来源。

不新增数据库依赖作为前提。可先评估版本化快照加追加日志，数据面通过明确的存储接口使用；管理层确定持久位置和权限，特权助手不得因运行用户不同而读到另一份空账本。状态与恢复继续遵循现有模块及所有权边界。

### 5.3 写入与恢复契约

顺序必须是：**分配并持久提交归属 → 对当前引擎可见 → 返回包含 Fake-IP 的 DNS 答案。** 不能先回复、后台再保存；否则崩溃窗口内已被客户端缓存的地址仍会丢失归属。已有归属命中无需每次写盘；允许有界批量提交，但每个 DNS 响应必须等到包含自身归属的批次已提交。

要求单写者/排他锁、版本与双向一致性校验、保留地址校验、截断/损坏检测和可验证的崩溃恢复。持久化失败时拒绝发布新地址；不要以空表继续使用原池。当前配置文件的临时写入加 rename 可作参考，但不能未经验证就当作完整的跨平台日志及断电一致性方案。

启动时先恢复并校验账本，再接管路由/发布 DNS。无法确认旧状态完整时，保留诊断信息，恢复有效状态或换用经过冲突检查的新池；不能猜测旧地址对应哪个域名。规则撤销与配置回退不得把地址账本回滚到更早的分配历史。人为删除全部状态、恢复旧磁盘备份等情形不在“正常重启稳定”的保证内，必须作为状态丢失处理。

### 5.4 容量不能留到实现后再处理

不跨域复用地址会消耗池容量：当前默认 IPv4 `/16` 在引擎保留地址后约有 6.5 万槽；管理配置常用 IPv6 `/120` 在保留后只有 **253 个**可分配地址。当前分配器还有 `0x3ffff` 容量上限，单纯把 IPv6 前缀写大不会无限扩大实际空间。

因此持久归属不能孤立上线：必须同时确定容量告警、内存/磁盘限额及耗尽行为，并评估扩大 IPv6 池与稀疏分配结构。空间不足时保留已有归属、新申请明确失败，不自动回收旧地址给其他域名；不能将每次普通重启当作清空容量的方法。

长期可用性可通过受控启用新池、保留旧池映射或拒绝旧池请求来扩展。新旧池的路由、LAN/VPN 冲突、未知旧地址和回退均须验收；仅移除旧捕获路由可能把旧缓存流量交给其他真实网络路径，不构成安全退役。若产品选择有限保留期后跨域复用，必须明确接受残余错关联风险，这不属于本文推荐的保证。

## 6 3.2：产品限制与未来手册文案

用户已决定将此项作为产品限制。保留“应用持有真实 IP 时不能可靠恢复域名”的边界，不建立一个把最近 DNS 查询绑定到所有同 IP 流量的全局反向猜测表；共享 CDN 会使这种做法误伤其他域名。

后续在配置指南的规则生效范围和排障指南加入以下内容，本轮仅在 proposal 中保留草案：

> 域名规则依赖连接可用的域名信息。应用若继续使用之前缓存的真实 IP，或通过 KONE 未观察到的解析路径取得地址，新建连接也可能无法匹配新增域名规则。配置保存成功表示新策略已发布，不表示所有应用缓存和现有连接已经更新。请让应用重新解析域名并建立新连接；必要时按该应用支持的方式清理缓存或重启。仅刷新页面或清空系统 DNS 缓存不保证奏效。

补充说明：已有长连接保留原策略；使用旧 Fake-IP 新建流与使用旧真实 IP 新建流是不同情形。可查看实际连接的域名来源、配置版本与命中规则；KONE 未观察到的连接不能显示为已验证。后台 Smart 建议也必须遵守这一生效边界，见[DNS 驱动建议 proposal](dns-driven-smart-suggestions.md)。

## 7 兼容迁移与模块边界

四池会改变旧混排规则的跨类顺序，应作为显式规则语义版本升级处理。旧配置按旧语义读取并提供转换预览；转换按类型分池且保留各池原相对顺序，列出可能改变结果的 IP/域名交叉优先关系。不能只排序存储数组而悄悄宣称配置行为未变。模式、规则语义版本、捕获路由和保护计划仍须一次发布；失败按已有事务回滚。

新持久分配器首次接管旧内存池时，不一定能恢复所有曾发给客户端的地址。可以导入可验证的当前归属，但丢失历史不能靠重新哈希恢复；无法完整接续时采用明确的新池迁移，并提示旧缓存需要重新解析。回退到不理解新账本的旧二进制也不得无条件复用新池。

| 模块 | 后续工作 |
| --- | --- |
| `pkg/kone/rule.go` / 配置校验 | 分池编译、证据状态、稳定规则身份、条件与迁移语义 |
| `pkg/kone/dns.go` / 解析缓存 | 合规补解析、CNAME 证据、DNS 阶段延迟决定、真实答案与 Fake-IP 的选择 |
| `pkg/kone/flow.go` / 出站 | 消费不可变地址计划；直连与代理均不得偏离获准目标；保留旧流快照 |
| `pkg/kone/dns_table.go` / 地址池 | 归属与 TTL 缓存解耦、恢复/保留/耗尽、并发及未知地址失败 |
| `pkg/control` / `pkg/desktop` | 存储位置、授权与单写者、助手重建、迁移预览和生命周期恢复 |
| 模拟/观察 API 与后续界面 | 展示池、证据、候选与实际目标；未知不伪装成 FINAL；沿用版本检查 |

Standalone、Global、Smart、Custom 的模式定义保持独立。四池是需要执行规则时的共同语义；Standalone/Global 不因此暗中启用业务自定义规则。Smart 第一期的后台探测只生成建议，不写入这些池；用户接受后才形成相应规则。

## 8 后续实施顺序与验收

建议先落地求值与候选一致性的纯逻辑回归，再接 DNS/流路径；持久归属可单独开发，但在容量、升级与故障恢复验收前不宣称解决 3.4。最后同步 PRD、配置/排障手册及配置迁移说明。本 proposal 不授权提前实施上述变更。

| 验收组 | 必须证明的结果 |
| --- | --- |
| 四池 | 任意混排输入都得到固定跨池优先级；池内顺序、到期及条件行为稳定；系统保护不被业务规则覆盖 |
| 3.1 | 冷/热缓存下的 IP 例外一致；无域名匹配时先补证据；必要 DNS 失败不被当作 FINAL 命中 |
| 域名/CNAME | 原始域名优先的建议语义明确；别名链有效性与上限；无关回答不参与决策；端口/协议未知时不误判 |
| 3.3 | 调换 A/AAAA 答案顺序、混合网段和动作、直连与代理、重试和 TTL 刷新，均不出现规则匹配 B 却拨号 A |
| 地址族与捕获 | 实际路由范围覆盖预期新流；IPv4/IPv6 候选按能力处理；Fake-IP 不被 LAN 保护直接旁路 |
| 3.4 | 碰撞域名、反序查询、正常重启、强杀/断电故障注入、缓存淘汰后保持归属；DNS 发布前持久提交 |
| 状态与容量 | 损坏/缺失/旧快照、写盘失败、重复启动、跨 profile/CLI、保留地址变化、池耗尽和迁移都有明确结果 |
| 3.2 | 用户指南清楚说明限制；旧真实 IP 不被伪归属，新 Fake-IP 按新规则决定；旧会话不被隐式重放或迁移 |
| 平台 | 单元测试之外，隔离 Linux/macOS/Windows 原生验证真实 DNS、捕获、重启、升级和恢复；不在用户主机改网络 |

需要评审的具体取舍：原始域名与 CNAME 的优先关系；多地址的规则优先选择及拒绝语义；持久归属的容量/池迁移方案；旧配置升级与未来纯应用规则位置。前两项决定路由语义，容量方案决定 3.4 的保证能否长期成立，不宜留作未说明的实现细节。
